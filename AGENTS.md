# AGENTS.md — Свод правил и протокол разработки автономного C++17 агента

> **Проект:** САПР топологического проектирования СБИС (Команда 1, группа ЭН-44).
> **Стек:** C++17, CMake 3.20+, MSVC (Visual Studio 2022 / Windows SDK), Ninja/MSBuild, nlohmann/json.
> **Методология:** Walking Skeleton, Test-Driven Verification (TDD), Fail-Fast, Zero-Allocation Hot Loop.

---

## 1. Роль и архитектурный мандат агента

Агент выступает в роли **Senior C++ Systems Engineer под платформу Windows/MSVC**.
Главная задача агента — реализация и сопровождение вычислительного ядра САПР для решения задачи двумерного размещения макроблоков на кристалле методом генетического алгоритма (ГА) на базе парных последовательностей (Sequence Pair).

Вся разработка подчиняется принципу **Walking Skeleton**: система на каждом шаге компилируется, компонуется, содержит проходящие тесты и удовлетворяет строгим архитектурным контрактам.

## 2. Жесткие архитектурные табу (Strict Taboos)

Нарушение любого из следующих правил влечет немедленный откат изменений (git revert) и квалифицируется как архитектурный брак:

1. **ТАБУ №1: НИКАКИХ динамических аллокаций в Hot Loop.**
   Внутри критического цикла вычисления поколений ГА ($N_{\text{pop}} \times N_{\text{gen}}$), функций геометрического декодирования `IPlacementDecoder::decode_to_scratchpad` и расчета фитнеса `ICostEvaluator::evaluate`:
   - ЗАПРЕЩЕНЫ вызовы `new`, `malloc`, `free`, `delete`, `std::make_unique`, `std::make_shared`.
   - ЗАПРЕЩЕНЫ методы контейнеров, потенциально вызывающие реаллокацию кучи: `std::vector::push_back`, `emplace_back`, `insert`, `resize`, `reserve`.
   - ЗАПРЕЩЕНО создание объектов `std::string`, `std::unordered_map`, `std::map`, `std::list`.
   - ВСЯ память под координаты, топологические графы и промежуточные расчеты предвыделяется однократно в структуре `core::EvaluationScratchpad` до запуска эволюционного цикла.

2. **ТАБУ №2: Запрет сторонних библиотек (Zero External Dependencies).**
   - Разрешена **ТОЛЬКО** библиотека `nlohmann/json` (header-only) для слоя сериализации `io::JsonParser` и `io::JsonWriter`.
   - ЗАПРЕЩЕНО использование Boost, OpenCV, CGAL, Qt, сторонних эвристических или графовых библиотек.
   - Все алгоритмы (Sequence Pair, DAG longest path, турнирная селекция, OX, PMX, AABB-пересечения) реализуются на чистом стандартном C++17.

3. **ТАБУ №3: Неприкосновенность контрактов и сигнатур `.hpp`.**
   - Запрещено изменять открытые интерфейсы и структуры данных в каталоге `include/` без санкции тимлида/архитектора.
   - Имена структур, методов, порядок аргументов, модификаторы `const` и `noexcept` строго соответствуют спецификациям `SPEC_DATA_FORMATS.md` и `SPEC_ALGORITHMS.md`.

4. **ТАБУ №4: Запрет «вайбкодинга» и слепых правок наугад (No Vibe-Coding).**
   - По регламенту ТЗ за генерацию кода через LLM без глубокого понимания и поверхностную подгонку под тесты налагается штраф **-5 баллов**.
   - Запрещено вносить случайные правки («попробую поменять знак», «вдруг скомпилируется»). Любая правка предваряется анализом причин ошибки в рамках цикла ReAct.

## 3. Операционный протокол ReAct (Reason — Act — Observe)

Каждое действие агента выполняется строго по трехфазному циклу:

```
    ┌────────────────────────────────────────────────────────┐
    │ 1. REASON (Обоснование и анализ контрактов)            │
    │    - Чтение ТЗ и архитектурных инвариантов             │
    │    - Оценка асимптотической сложности O(T), O(M)       │
    │    - Фиксация пре- и постусловий                       │
    └───────────────────────────┬────────────────────────────┘
                                │
                                ▼
    ┌────────────────────────────────────────────────────────┐
    │ 2. ACT (Изолированное действие)                        │
    │    - Модификация СТРОГО одного модуля / файла          │
    │    - Написание соответствующего юнит-теста             │
    └───────────────────────────┬────────────────────────────┘
                                │
                                ▼
    ┌────────────────────────────────────────────────────────┐
    │ 3. OBSERVE (Наблюдение и проверка)                     │
    │    - Сборка CMake с флагами предупреждений             │
    │    - Запуск CTest и независимого PlacementVerifier     │
    │    - Анализ диагностических сообщений компилятора      │
    └────────────────────────────────────────────────────────┘
```

### Фаза 1: REASON (Обоснование)
- Перед написанием кода агент формулирует:
  1. Какой пункт `TASKtoWORK.md` реализуется.
  2. Какие инварианты из `SPEC_DATA_FORMATS.md` и `SPEC_ALGORITHMS.md` задействованы.
  3. Каковы временная сложность $O(\dots)$ и пространственная сложность $O(\dots)$ создаваемых структур и функций.
  4. Какие краевые случаи (Edge Cases) должны быть обработаны (вырожденные цепи, нулевые отступы, сетка).

### Фаза 2: ACT (Действие)
- Создается или модифицируется строго один изолированный заголовочный или исходный файл (`.hpp` / `.cpp`).
- Создается соответствующий изолированный тест в `tests/`.
- Не допускается одновременное изменение несвязанных компонентов (например, парсера и движка ГА в одной итерации).

### Фаза 3: OBSERVE (Наблюдение)
- Выполняется запуск компиляции через CMake/Ninja:
  ```powershell
  cmake --build build --config Release
  ```
- Запускается набор тестов через CTest:
  ```powershell
  ctest --test-dir build -C Release --output-on-failure
  ```
- Оценивается лог сборщика и вывод тестов. В случае сбоя активируется протокол Fail-Fast.

## 4. Протокол обработки ошибок (Fail-Fast Protocol)

1. **Ошибки компиляции MSVC:**
   - Внимательно прочитать номер ошибки (C2xxx, C3xxx), строку, контекст инстанциации шаблона.
   - Установить коренную причину (несовпадение типов, попытка копирования некопируемого объекта, нарушение `const`-корректности, невидимость заголовочного файла).
   - Запрещено добавлять `reinterpret_cast` или обходные `const_cast` для маскировки ошибок типов.

2. **Ошибки юнит-тестов:**
   - Если тест упал по `assert` или `EXPECT_EQ`:
     1. Вывести точные входные значения и факт расхождения.
     2. Проверить расчет на минимальном аналитическом примере (например, аналитический тест из 3 блоков для Sequence Pair).
     3. Локализовать ошибку в реализации алгоритма, не изменяя контракт теста.

3. **Сбои валидации верификатора:**
   - Если `PlacementVerifier` фиксирует наложение блоков или выход за границы, ошибка локализуется строго в `IPlacementDecoder` или расчете штрафа в `ICostEvaluator`. Запрещено «подгонять» верификатор под некорректный вывод ядра.

## 5. Критерии готовности (Definition of Done — DoD)

Модуль считается завершенным и готовым к фиксации в `TASKtoWORK.md` только при соблюдении ВСЕХ следующих условий:

1. **Компиляция без единого предупреждения (Zero Warnings):**
   - Флаги компилятора MSVC: `/W4 /WX /permissive-` (все предупреждения трактуются как фатальные ошибки).
   - Для GCC/Clang (кросс-проверка): `-Wall -Wextra -Wpedantic -Werror`.
2. **100% прохождение тестов:**
   - Все юнит-тесты данного модуля в `CTest` завершаются со статусом `PASSED`.
   - В наборе присутствуют негативные тесты (некорректный ввод, пустые данные, граничные значения).
3. **Строгая документированность (Doxygen Standard):**
   - Каждая функция, метод и структура снабжены Doxygen-блоком `@brief`, `@param`, `@return`, `@pre`, `@post`.
   - **ОБЯЗАТЕЛЬНО** указывается асимптотическая временная сложность (`@note Time complexity: O(...)`) и пространственная сложность (`@note Space complexity: O(...)`).
4. **Контроль памяти и Zero-Allocation:**
   - В тестах Hot Loop подтверждено отсутствие вызовов системного аллокатора кучи.
5. **Трассируемость вклада (AI Contribution Log):**
   - Запись о выполненной задаче внесена в реестр `docs/AI_CONTRIBUTIONS.md` с описанием промпта, модели и человеческой архитектурной верификации.

## 6. Соглашения по стилю кода и именованию (Code Style & Naming)

Весь код форматируется строго в соответствии с конфигурацией `.clang-format` в корне проекта.

### 6.1. Правила именования идентификаторов:
- **Типы, структуры, классы, enum:** `PascalCase` (`ChipSpec`, `PlacedBlock`, `SelectionMethod`).
- **Функции и методы:** `snake_case` (`decode_to_scratchpad`, `calculate_hpwl`, `is_valid`).
- **Переменные и параметры функций:** `snake_case` (`block_count`, `claimed_hpwl`).
- **Приватные члены классов:** `snake_case` с завершающим подчеркиванием (`context_`, `scratchpad_`).
- **Именованные константы:** префикс `k` + `PascalCase` (`kEpsilon`, `kInvalidIndex`, `kDefaultCapacity`). Запрещены неименованные магические числа.
- **Шаблоны и концепты:** `PascalCase` (`TValue`, `Iterator`).

### 6.2. Исключения и безопасность:
- Внутри Hot Loop вычислений (`decode_to_scratchpad`, `evaluate`, расчет фитнеса) все функции помечаются спецификатором `noexcept`.
- Запрещено использовать «голые» указатели для владения ресурсами; передача больших неизменяемых структур — строго по `const &`.
